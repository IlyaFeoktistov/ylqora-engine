# Архитектура сцены: узлы, компоненты, ресурсы

[English version](scene.md)

Это контракт для всего, что живёт в сцене: что такое узел, что такое
компонент, как регистрируются типы, жизненный цикл и как на это опираются
скрипты, редактор и горячая перезагрузка. Меняется вместе с кодом.

Пометки статуса: **[done]** сделано, **[next]** следующий этап работы (до
скриптов на C++), **[planned]** позже, с шагом, к которому относится.

## Принятые решения

1. **Игра добавляет компоненты, а не типы узлов.** Типы узлов даёт только
   движок. Игра по-прежнему создаёт в коде узлы типов движка (`Node`, `Node3D`,
   `Camera3D`, ...) и подключает к ним свои компоненты. Дерево типов узлов не
   меняется, когда модуль игры перезагружают.
2. **Скрипт - это компонент.** Сам по себе в мире он существовать не может,
   только на узле. Каждый класс скрипта - свой тип компонента: и в C++, и в
   Luau, и в визуальных скриптах.
3. **По умолчанию один компонент типа на узле.** Повторение тип разрешает
   явно через `.allowMultiple()`.
4. **Ядро не предполагает 3D.** В MVP сделано только 3D, 2D идёт после него
   отдельным семейством рядом с 3D, а не внутри него.
5. **Рендер, физика и звук - компоненты на узле, а не типы узлов.** Меш - это
   `MeshRenderer` на `Node3D`; 2D-спрайт будет `SpriteRenderer` на `Node2D`.
6. **Языки скриптов:** сначала C++ (MVP), после MVP - Luau, после 2D -
   визуальные скрипты.

## Основные понятия

| | Что это | Кто задаёт типы | Примеры |
|---|---|---|---|
| **Узел** | Объект сцены со своей ролью, одна строка в дереве сцены | только движок | `Node`, `Node3D`, `Camera3D`, свет, элементы интерфейса |
| **Компонент** | Способность или поведение, подключённое к узлу | движок и игра | `MeshRenderer`, `RigidBody`, `BoxCollider`, `AudioSource`, скрипты |
| **Ресурс** | Файл проекта с постоянным ID | движок (форматы) | меш, материал, шейдер, текстура, звук, сцена, исходник скрипта |

Как выбрать:

- Объект без этого не имеет смысла и виден в дереве как самостоятельная вещь
  (камера, свет): **узел**.
- Это добавка, которая подходит многим разным объектам: **компонент**.
- Это данные, общие для нескольких объектов: **ресурс**, а компонент на него
  ссылается.

## Иерархия узлов

```
Node                     без положения: группа, корень, носитель скриптов
├── Node3D               встроенный Transform3D (снять нельзя)
│   ├── Camera3D
│   └── DirectionalLight3D, PointLight3D, SpotLight3D      [planned, step 5]
├── Control              встроенный RectTransform, якоря   [planned, step 8]
│   └── Label, Button, ...
└── Node2D               встроенный Transform2D            [planned, after MVP]
    └── Camera2D, ...
```

- `Node2D` не наследует `Node3D` и наоборот: у трансформов разный смысл. Общие
  у них только `Node`, дерево, жизненный цикл и инфраструктура редактора.
- Класс узла хранит свойства своей роли (угол обзора, цвет света) и
  регистрируется в системах сцены в `onEnterScene` / `onExitScene`. **Никакой
  игровой логики в классах узлов**: покадровая работа узлов движка
  принадлежит их системе. `onStart` / `onUpdate` / `onStop` есть только у
  компонентов **[done]**.

## Компоненты

### Регистрация и правила [done]

```cpp
registry.registerComponent<MeshRenderer>()
    .requiresNode<Node3D>()               // на каких узлах может жить
    .property("mesh", &MeshRenderer::mesh, &MeshRenderer::setMesh, PropertyHint::Mesh);

registry.registerComponent<BoxCollider>()
    .requiresNode<Node3D>()
    .requiresComponent<RigidBody>();      // нужен RigidBody на том же узле

registry.registerComponent<AudioSource>()
    .requiresNode<Node3D>()
    .allowMultiple();
```

- `requiresNode<T>()`: владелец должен быть `T` или его наследником.
- `requiresComponent<T>()`: на том же узле должен быть компонент типа `T` или
  его наследника. Редактор добавляет его вместе с зависимым, одним шагом
  отмены. Обязательный компонент нельзя снять, пока от него что-то зависит: у
  его заголовка нет крестика, а в подсказке названы зависимые. Зависимые
  никогда не снимаются неявно.
- `allowMultiple()`: несколько компонентов этого типа на одном узле. Каждый
  экземпляр всё равно проверяется по `requiresNode` и `requiresComponent`.
- Правила наследуются: правила базового типа компонента действуют и на
  наследников.
- Базовый тип берётся из `YQLORA_TYPE(Class, Base)`, а не из второго
  параметра шаблона регистрации, и регистрация не компилируется, если класс
  не наследует эту базу **[done]**.

`requires` - ключевое слово C++20, отсюда `requiresNode` / `requiresComponent`.

### Кто проверяет правила

Сами проверки - свободные функции в `ComponentRules.hpp` (`canAttach`,
`missingRequirements`, `dependentsOf`); все ниже вызывают их.

- Редактор, через `EditorSession` **[done]**.
- Загрузчик сцены: компонент на неподходящем узле пропускается с ошибкой в
  логе; недостающий обязательный компонент добавляется с предупреждением
  **[done]**.
- Сам `Node::addComponent`, для узла в сцене: сначала добавляет недостающие
  обязательные компоненты, как `AddComponent` в Unity, а нарушение правила -
  ошибка программы, так что и код игры их не обойдёт **[done]**.

### Встроенные компоненты

Пространственный узел создаёт свой трансформ в конструкторе (`Transform3D` у
`Node3D`). Его нельзя снять, и его нет в "Добавить компонент".

## Скрипты на C++ [planned, step 2]

```cpp
class Player : public yqlora::Script {
public:
    YQLORA_TYPE(Player, Script)

    float speed = 5.0f;

protected:
    void onUpdate(float deltaSeconds) override;
};

// В модуле игры:
registry.registerComponent<Player>().property("speed", &Player::speed);
```

- `Script` - это `Component` с полным жизненным циклом и доступом к контексту
  движка. Скрипты регистрируются в модуле игры (`TypeRegistry::ModuleScope`)
  и по умолчанию разрешают несколько штук на узле.
- Файл исходника скрипта - ресурс; сцена ссылается на скрипт по имени его
  типа компонента.
- Исключение из вызова жизненного цикла перехватывается: компонент
  выключается, ошибка идёт в лог. Игровой цикл продолжается. Ошибку памяти в
  нативном коде не перехватить; это цена скриптов на C++.

## Скрипты на Luau [planned, after MVP]

[Luau](https://luau.org) (MIT): Lua 5.1 с постепенной типизацией, встроенной
песочницей и языковым сервером.

- Каждый скрипт `.luau` регистрирует в реестре **свой тип компонента** с
  именем скрипта и свойствами, объявленными в скрипте. Все они создают
  экземпляры одного C++-класса, `LuauScript`, привязанного к ресурсу скрипта.
  Поэтому реестр должен принимать типы и свойства, заданные во время
  выполнения, а не только из шаблонов C++ **[next]**: свойства уже со стёртым
  типом (`std::function` над `void*`), а построитель - нет.
- Привязки генерируются из реестра: свойства плюс **зарегистрированные
  методы** типов движка **[next]**. Один список служит Luau, инспектору и
  документации API. Из того же списка получаются файлы определений типов для
  luau-lsp, которые дают автодополнение и проверку типов в редакторе кода.
- Песочница: собственная у Luau (`luaL_sandbox`: глобальные только для
  чтения, нет доступа к `io` / `os`), обработчик прерываний против
  бесконечных циклов, распределитель памяти с ограничением.
- Ошибка Luau выключает компонент и идёт в лог, как исключение C++.
- Скрипты Luau - свой модуль типов (`luau`), перезагружаются как `game.dll`.

## Визуальные скрипты [planned, after 2D]

Для тех, кто не пишет код: скрипт собирается из блоков, соединённых связями,
потом вешается на узел и работает как скрипт на C++ или Luau.

- Граф - ресурс (файл проекта): блоки, их выводы и связи между ними. Связи
  выполнения задают порядок действий, связи данных передают значения.
- Каждый граф регистрирует **свой тип компонента**, как скрипт Luau, со
  свойствами, объявленными в графе. Все они создают экземпляры одного
  C++-класса, `VisualScript`, привязанного к ресурсу графа.
- Входные блоки - вызовы жизненного цикла (`onStart`, `onUpdate`, `onStop`),
  позже события (ввод, столкновения).
- Палитра блоков генерируется из того же списка реестра, что и привязки Luau:
  свойства и зарегистрированные методы типов движка и игры. Новый метод типа
  становится блоком без дополнительной работы.
- Движок интерпретирует граф. Ограничение числа шагов на вызов защищает от
  бесконечных циклов; ошибка выключает компонент и идёт в лог, как исключение
  C++.
- Визуальные скрипты - свой модуль типов (`visual`), перезагружаются при
  сохранении графа.
- Редактор графов - панель редактора; логика правки отделена от ImGui, как и
  весь редактор.

## Контекст движка

Три уровня: что общее у процесса, чем владеет каждая сцена, что видит
компонент.

```
Владелец (игра / редактор / тест)
 └─ EngineServices     общее у процесса: ввод, проект, реестр типов, запросы сцен
     └─ Scene          своё у каждой сцены
         ├─ GameTime        игровое время, шкала времени, фиксированный шаг
         ├─ systems         рендер, физика, звук... (подключаемые)
         ├─ phase lists     кого вызывать в fixedUpdate / update / lateUpdate
         └─ дерево узлов
             └─ Component → owner()->scene() → services(), time(), system<T>()
```

### Службы движка [done]

```cpp
class EngineServices {
public:
    const Input& input() const;          // сырое состояние + действия из настроек проекта
    const Project* project() const;      // настройки и ресурсы; nullptr, если проекта нет
    const TypeRegistry& registry() const;
    SceneRequests& scenes();             // "загрузить уровень": между кадрами  [planned, step 9]
};
```

- Сцена получает службы при создании: `Scene(const EngineServices&)`. Тесты и
  пустые сцены получают службы, где ничего не нажато и проекта нет, поэтому
  нигде нет проверок на `nullptr`.
- Нет `Application::instance()`. Лог и перевод остаются глобальными по
  решению.
- Реестр в службах - это то, что позволяет `Node::addComponent` самому
  проверять правила компонентов и что сообщает сцене фазы жизненного цикла
  типа.
- В редакторе копия для Play видит ввод, только пока окно сцены в фокусе,
  чтобы клавиши, набранные в инспекторе, не двигали игрока.

### Игровое время [done]

```cpp
class GameTime {
public:
    double elapsed() const;          // с начала игры, по шкале
    float delta() const;             // этот кадр, по шкале
    float unscaledDelta() const;     // реальный шаг: редактор, анимации HUD
    float fixedStep() const;         // из раздела Time настроек проекта
    float scale() const;
    void setScale(float scale);      // 0 останавливает игру, 0.5 - замедление
    std::uint64_t frame() const;
};
```

У каждой сцены своё; копия для Play начинается с нуля, пауза его
останавливает. Реальная длина кадра берётся из `FrameClock`, игровое время
выводится из неё.

### Системы сцены [next]

Главная точка расширения: модуль добавляет систему и её компоненты; `Scene`,
цикл кадра и приложение не меняются.

```cpp
class SceneSystem {
public:
    virtual ~SceneSystem() = default;
    virtual void fixedUpdate(float step) {}    // здесь шагает физика
    virtual void update(float delta) {}
    virtual void lateUpdate(float delta) {}    // после скриптов: список рендера, звук
};

// Модуль регистрирует фабрику один раз; каждая новая сцена получает экземпляр:
systems.add<PhysicsWorld>([](Scene& scene) { return std::make_unique<PhysicsWorld>(scene); });
scene.system<PhysicsWorld>()                    // компонент регистрирует тело в onEnterScene
```

У редактируемой сцены в редакторе тоже есть системы (тела существуют,
коллайдеры можно нарисовать), но шагает только копия для Play.

### Один кадр [next]

Порядок живёт в одном месте, `Scene::advance`:

```
scene.advance(realDelta):
    time.advance(realDelta)                       шкала, накопитель фиксированного шага
    пока накоплен фиксированный шаг:
        systems.fixedUpdate, затем components.onFixedUpdate
    components.onUpdate
    systems.update
    components.onLateUpdate
    systems.lateUpdate
    применить отложенные изменения дерева         удаление, смена родителя
```

Игра (`Application`) вызывает `advance` каждый кадр, `PlayMode` редактора
вызывает его для копии Play, когда она не на паузе, тесты вызывают напрямую.
Сейчас `advance` делает фазы и фиксированный шаг; системы и отложенные
изменения появятся вместе со своими пунктами ниже.

## Пайплайн кадра

Весь кадр движка, а не только часть сцены. У каждого этапа один владелец;
порядок живёт в одном классе цикла кадра, который знает только порядок
**[next]**.

```
1. Begin       FrameClock: длина кадра
2. Input       события окна -> сырой ввод -> действия из настроек проекта
3. Simulate    scene.advance: фиксированные шаги (физика) -> update -> late update
               -> отложенные изменения дерева
4. Transforms  мировые матрицы изменённых узлов, один проход с флагом "грязный"
5. Extract     система рендера снимает с сцены снимок кадра: виды (камеры),
               что рисовать, свет. После этого сцену никто не читает.
6. Render      подготовка: отсечение по видимости и маске слоёв для каждого вида,
               сортировка (непрозрачное спереди назад, прозрачное сзади вперёд)
               граф: проходы рендера (тени, непрозрачное, небо, прозрачное,
               постобработка, HUD) через RHI
7. Interface   ImGui редактора и инструментов
8. Present
```

- **Снимок из Extract** - единственное, что читает рендер; сцену он не
  трогает. Потом рендер можно вынести в свой поток (игра считает кадр N+1,
  пока рисуется кадр N), не меняя игровой код. Сейчас `buildFrameData` уже
  по сути Extract; он станет частью системы рендера вместе со списком видов,
  камерами, слоями и масками **[next]**.
- **Мировые матрицы** обновляются одним проходом по изменённым узлам, между
  симуляцией и Extract **[next]**.
- **Граф рендера**: проход объявляет, что читает и что пишет, граф
  выстраивает порядок проходов. Новый эффект - ещё один проход, а не правка
  рендера. Редактор добавляет в граф свои проходы (сетка, контур выделения),
  и `FrameData::editor` уходит. Вместе с ним появятся отсечение и сортировка
  **[planned, RHI]**.
- **Поток рендера** появится, когда понадобится; снимок из Extract это уже
  позволяет **[planned, later]**.

## Жизненный цикл

| Вызов | Где | Для чего |
|---|---|---|
| конструктор | где угодно | значения по умолчанию; сцены ещё нет |
| `onEnterScene` / `onExitScene` | редактор и игра | регистрация в системах сцены (физика, звук, свет) |
| `onEnable` / `onDisable` | только игра | компонент начинает или перестает участвовать: включён и его узел активен в иерархии **[next]** |
| `onStart` | только игра | один раз, перед первым вызовом фазы компонента |
| `onFixedUpdate(step)` | только игра | физика, фиксированный шаг игрового времени **[done]** |
| `onUpdate(delta)` | только игра | логика кадра |
| `onLateUpdate(delta)` | только игра | после всех update: камеры, которые следуют за целью **[done]** |
| `onStop` | только игра | освободить взятое в `onStart` |

### Списки фаз вместо обхода дерева [done]

- Сцена держит по списку на фазу (фиксированный шаг, update, late update) и
  вызывает только компоненты из него. Компонент попадает в список, только
  если его тип переопределил эту фазу; реестр узнаёт это при регистрации
  типа (`PhaseDetector` сравнивает класс, где объявлен `onUpdate` и
  остальные; `YQLORA_TYPE` делает его другом класса). Ни обхода дерева, ни
  пустых виртуальных вызовов.
- Порядок внутри фазы: **порядок выполнения** типа (по умолчанию 0, меньше -
  раньше), затем порядок, в котором компоненты вошли в список. Тип задаёт
  значение по умолчанию в коде (`.executionOrder(-100)`); настройки проекта
  могут переопределить его для типа, как Script Execution Order в Unity (см.
  [настройки проекта](project-settings.ru.md)). Одно правило: значение из
  настроек, если оно есть, иначе значение по умолчанию из кода.
- Компонент, добавленный во время фазы, вызывается со следующей фазы;
  снятый пропускается сразу и убирается из списка после фазы, так что списки
  никогда не меняются под обходом.

### Активность и включённость [next]

Как в Unity:

- У узла есть `active` (свой флаг) и `activeInHierarchy()` (он и все его
  родители активны). Неактивный узел выключает всю свою ветку: компоненты
  получают `onDisable`, уходят из списков фаз, рендереры не рисуются, тела
  уходят из мира физики.
- У компонента есть `enabled`. Он участвует в игре, только пока включён и его
  узел активен в иерархии; `onEnable` / `onDisable` отмечают смену.
- Отдельного флага `visible` нет: спрятать меш - выключить его
  `MeshRenderer`, как `Renderer.enabled` в Unity.
- У узла есть **слой** (один из 32, имена в настройках проекта). Маски камер и
  столкновения физики фильтруют по слоям.
- Исключение из вызова жизненного цикла перехватывается: компонент
  выключается, ошибка идёт в лог, игра продолжается.

### Отложенные изменения дерева [next]

Удаление узла и смена его родителя во время кадра применяются в конце кадра,
так что ни одна фаза не видит наполовину изменённое дерево. Узлы, созданные
во время кадра, участвуют со следующего.

## Камеры и рендер [next]

Подготовка к нескольким камерам (например, руки игрока рисует вторая камера
поверх мира, чтобы они не проваливались в стены); самих рук здесь нет.

- У `Camera3D` есть **порядок** (меньше - рисуется раньше), **маска слоёв** и
  **режим очистки**: цвет и глубина, только глубина, ничего.
- Система рендера собирает включённые камеры сцены, отсортированные по
  порядку. Данные кадра несут список видов вместо одной камеры; бэкенд рисует
  их по очереди, каждый со своей очисткой и только то, чей слой есть в его
  маске.
- **Главная камера** (первый вид, через который видна игра) - состояние
  системы рендера, а не `Scene`; камера, ушедшая из сцены, выпадает из списка
  сама. Сейчас `Scene::activeCamera()` - сырой `Camera3D*`, который сбрасывают
  вручную в нескольких местах.
- Смена сцены по запросу скрипта происходит между кадрами, никогда посреди
  update **[planned, step 9]**.

## Ссылки, состояние и сериализация

- Ссылка на узел - `NodeId`, на ресурс - `ResourceId`; оба - типы свойств.
  Сырой указатель на другой узел или компонент можно хранить только между
  `onEnterScene` и `onExitScene`, и при выходе его надо сбросить.
- **Зарегистрированные свойства сохраняются; всё остальное - состояние
  выполнения.** Копия для Play и горячая перезагрузка идут через
  сериализацию, поэтому переживают их только свойства. Это контракт для
  скриптов: всё, что должно пережить перезагрузку, - свойство.
- Сериализация восстанавливает состояние, но не управляет временем жизни:
  подписки, регистрации в системах и ресурсы освобождаются в `onStop` /
  `onExitScene` до выгрузки модуля.

## Горячая перезагрузка [planned, step 3]

1. Остановить игру, если она идёт.
2. Сериализовать сцену; забрать из неё всё дерево, чтобы каждый компонент
   получил `onExitScene` и после этого не выполнялся код старого модуля.
3. Уничтожить дерево, `TypeRegistry::removeModule`, очистить индекс
   компонентов сцены по типам (сейчас ключ - `std::type_index`, который
   указывал бы в выгруженный код), выгрузить библиотеку.
4. Загрузить новую библиотеку, зарегистрировать её типы, загрузить сцену
   обратно.

Компонент, тип которого пропал (игра не собралась, скрипт удалили),
сохраняется как заглушка с его сырыми данными, показывается в инспекторе как
не найденный и записывается обратно без изменений при сохранении. Иначе
сохранение сцены молча потеряло бы данные **[planned, step 3]**.

## Связь с редактором

- Инспектор строится по свойствам и их подсказкам (`PropertyHint`). Свой
  инспектор для типа добавляется, только когда подсказок не хватает.
- "Добавить компонент" показывает только типы, которые подходят узлу:
  `requiresNode`, правило одного на узел и требования, которые можно
  выполнить **[done]**.
- Гизмо для типа живут в `editor/ui/gizmos` (как `CameraGizmo`); движок про
  них ничего не знает.
- Вспомогательная графика редактора (сетка, контур выделения) уходит из
  данных кадра движка вместе с появлением слоя над графическим API, до
  шага 5.

## Раскладка кода

Каждая система - отдельная папка со своей регистрацией типов;
`registerEngineTypes` только вызывает их.

```
engine/include/yqlora/scene/     Node, Node3D, Transform3D, Component, Script, Scene
engine/include/yqlora/render/    MeshRenderer, Camera3D, свет
engine/include/yqlora/physics/   RigidBody, коллайдеры, PhysicsWorld     [step 6]
engine/include/yqlora/audio/     AudioSource, AudioListener, AudioWorld  [step 7]
engine/include/yqlora/ui/        Control, Label, Button                  [step 8]
```

Перенос `MeshRenderer` и `Camera3D` в `render/` - часть следующего этапа.
