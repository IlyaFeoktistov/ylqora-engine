# Настройки проекта

[English version](project-settings.md)

Настройки игры, которые лежат в папке её проекта, общие для всех, кто над ней
работает, и попадают в систему контроля версий: действия ввода, шаг времени,
графический API, физика, цели сборки. В редакторе: **Проект → Настройки
проекта**.

Пометки статуса как в [README](README.ru.md): **[done]**, **[next]** (до
скриптов на C++), **[planned, step N]**.

Не путать с **настройками редактора** (тема, язык, скорость камеры): они
принадлежат пользователю, лежат в профиле пользователя (`Settings`) и никогда
не попадают в проект.

## Принятые решения

1. **Раздел настроек - класс с зарегистрированными свойствами**, в том же
   реестре типов, что узлы и компоненты (`TypeKind::Settings`). Одно описание
   даёт формат файла, окно редактора (тот же редактор свойств, что в
   инспекторе) и доступ из кода. Второго списка полей нет нигде.
2. **Каждый раздел принадлежит своей системе.** Физика объявляет свой
   раздел, ввод - свой; класса со всеми настройками нет. Модуль игры может
   регистрировать свои разделы; они появляются в окне, как разделы движка, и
   уходят вместе с модулем при перезагрузке.
3. **Один файл на раздел**: `settings/<section>.json` в папке проекта. Меньше
   конфликтов слияния, понятная разница. Файлы входят в версию формата
   проекта: смена их формата означает миграцию и окно перевода проекта, как
   для сцен.
4. **Правки отменяются через Ctrl+Z**, через ту же историю правок, что и
   правки сцены. Поэтому история хранит команды над проектом, а не только над
   сценой.
5. **Ввод с самого начала идёт через действия.** Скрипты спрашивают
   `input.action("Jump")`, а не клавишу, поэтому смена привязок никогда не
   трогает код игры.

## Разделы

| Раздел | Содержимое | Когда |
|---|---|---|
| General | название игры, версия, компания, иконка, стартовая сцена | **[next]** |
| Time | фиксированный шаг времени, самый длинный кадр (сейчас константа `kMaxFrameSeconds`) | **[next]**, вместе с фиксированным шагом |
| Input | действия и оси, их привязки к клавишам, кнопкам мыши, геймпаду | **[next]** |
| Execution Order | порядок типов компонентов внутри каждой фазы жизненного цикла, переопределяет значение по умолчанию из кода (см. [сцену](scene.ru.md)) | **[next]** |
| Layers | имена 32 слоёв узлов для масок камер и физики | **[next]** |
| Graphics | графический API для каждой платформы (OpenGL; Vulkan и D3D12 появятся со слоем над графическим API), vsync | **[next]** |
| Scripts | сборка C++: компилятор, конфигурация; потом Luau | **[planned, step 3]** |
| Physics | гравитация, слои, матрица столкновений | **[planned, step 6]** |
| Audio | общая громкость, частота | **[planned, step 7]** |
| Display | разрешение, полноэкранный режим, можно ли менять размер окна | **[planned, step 9]** |
| Build | целевые платформы (Windows, Linux), сцены в игре, папка вывода, debug или release | **[planned, step 9]** |

Стартовая сцена переезжает из `project.yqlora` в General.

## Регистрация

```cpp
struct TimeSettings {
    YQLORA_SETTINGS(TimeSettings, "time")   // имя типа и имя файла

    float fixedStepSeconds = 1.0f / 60.0f;
    float maxFrameSeconds = 0.25f;
};

registry.registerSettings<TimeSettings>()
    .property("fixedStep", &TimeSettings::fixedStepSeconds)
    .property("maxFrame", &TimeSettings::maxFrameSeconds);
```

Точный макрос и построитель повторяют те, что у узлов и компонентов; важно,
что имя файла, имя типа и поля записаны один раз.

## Доступ

- Проект владеет одним экземпляром каждого зарегистрированного раздела,
  созданным со значениями по умолчанию и заполненным из его файла. Нет файла -
  значения по умолчанию; файл раздела, который больше никто не регистрирует,
  хранится как есть и записывается обратно без изменений, чтобы модуль,
  который не загрузился, не потерял свои настройки.
- Система читает свой раздел из проекта, с которым работает:
  `project.settings<PhysicsSettings>()`. Запуск игры без редактора (шаг 9)
  читает те же файлы.
- У настроек, которые нельзя менять на ходу (графический API), есть подсказка
  "нужен перезапуск"; окно пишет об этом рядом со значением. Все остальные
  применяются сразу, в том числе во время Play.

## Действия ввода

- У действия есть имя и вид: кнопка (нажата, удерживается, отпущена) или ось
  (значение от -1 до 1, от двух клавиш или стика).
- Привязка - это клавиша, кнопка мыши или кнопка либо ось геймпада. У одного
  действия любое число привязок.
- `Input` хранит сырое состояние (клавиши, мышь), как сейчас; действия - слой
  над ним, его читают скрипты и HUD.

## Слои

Как Tags and Layers в Unity:

- 32 слоя. Слой 0 - `Default`, есть всегда и не переименовывается; остальным
  имена даёт проект. Слой без имени не используется и в списках не
  показывается.
- Узел и маска камеры хранят номера слоёв, поэтому переименование слоя в
  сценах ничего не меняет. Если стереть имя слоя, на котором ещё есть узлы,
  редактор сначала спросит, а узлы останутся на нём.
- Список слоёв в инспекторе и маска камеры показывают имена и кончаются
  пунктом "Изменить слои...", который открывает этот раздел.
- Физика (шаг 6) берёт те же слои для своей матрицы столкновений.

## Что нужно реестру

- Свойства-списки (действия, привязки, слои): сейчас свойство хранит только
  одно значение.
- Тип свойства "привязка" (клавиша, кнопка мыши, ввод геймпада) с виджетом в
  редакторе: нажми, чтобы задать.
- Вид настроек (`TypeKind::Settings`) и его построитель.
