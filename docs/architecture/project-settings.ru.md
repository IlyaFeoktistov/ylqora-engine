# Настройки проекта

[English version](project-settings.md)

Настройки игры, которые лежат в папке её проекта, общие для всех, кто над ней
работает, и попадают в систему контроля версий: действия ввода, шаг времени,
графический API, физика, цели сборки. В редакторе: **Проект -> Настройки
проекта**.

Пометки статуса как в [README](README.ru.md): **[done]**, **[next]** (до
скриптов на C++), **[planned, step N]**.

Не путать с **настройками редактора** (тема, язык, скорость камеры): они
принадлежат пользователю, лежат в профиле пользователя (`Settings`) и никогда
не попадают в проект.

## Принятые решения

1. **Раздел настроек - класс с зарегистрированными свойствами**, в том же
   реестре типов, что узлы и компоненты (`TypeKind::Settings`). Одно описание
   даёт формат файла, окно редактора (тот же редактор свойств, что в
   инспекторе) и доступ из кода. Второго списка полей нет нигде.
2. **Каждый раздел принадлежит своей системе.** Физика объявляет свой
   раздел, ввод - свой; класса со всеми настройками нет. Модуль игры может
   регистрировать свои разделы; они появляются в окне, как разделы движка, и
   уходят вместе с модулем при перезагрузке.
3. **Один файл на раздел**: `settings/<section>.json` в папке проекта. Меньше
   конфликтов слияния, понятная разница. Файлы входят в версию формата
   проекта: смена их формата означает миграцию и окно перевода проекта, как
   для сцен.
4. **Правки отменяются через Ctrl+Z**, через ту же историю правок, что и
   правки сцены. Поэтому история хранит команды над проектом, а не только над
   сценой: она принадлежит `EditorSession`, а не документу сцены. Открытие
   другой сцены стирает историю вместе с правками настроек **[done]**.
6. **Сохраняются вместе с проектом, а не при каждой правке.** Правка
   действует сразу (и в Play), но в файл попадает только по "Сохранить"
   (Ctrl+S), которое пишет сцену и все изменённые разделы. Раздел изменён,
   пока его значения отличаются от файла (`ProjectSettings::modified`),
   поэтому правка, отменённая до прежнего значения, ничего не оставляет для
   сохранения. В заголовке "*", если не сохранены сцена или раздел; закрытие
   проекта и выход спрашивают про оба, открытие другой сцены - только про
   сцену, несохранённые настройки остаются **[done]**.
5. **Ввод с самого начала идёт через действия.** Скрипты спрашивают
   `input.action("Jump")`, а не клавишу, поэтому смена привязок никогда не
   трогает код игры.

## Разделы

| Раздел | Содержимое | Когда |
|---|---|---|
| General | название игры, версия, компания, стартовая сцена **[done]**; иконка | **[planned, step 4]** для иконки, вместе с текстурами |
| Time | фиксированный шаг времени, самый длинный кадр; сцена и цикл кадра читают их каждый кадр, поэтому правка применяется сразу, и в Play тоже | **[done]** |
| Input | действия и оси, их привязки к клавишам, мыши и геймпадам; см. [ввод](input.ru.md) | **[done]** |
| Execution Order | порядок типов компонентов внутри каждой фазы жизненного цикла, переопределяет значение по умолчанию из кода (см. [сцену](scene.ru.md)); тип выбирается из зарегистрированных компонентов, которые используют фазы кадра, строки незагруженных типов хранятся. Правка действует со следующего кадра, и в Play тоже: каждая запись раздела увеличивает `ProjectSettings::revision`, и списки фаз пересортировываются, когда он меняется | **[done]** |
| Layers | имена 32 слоёв узлов для масок камер и физики | **[done]** |
| Graphics | графический API для каждой платформы (OpenGL; Vulkan и D3D12 появятся со слоем над графическим API), vsync; оба применяются сразу, см. [рендер](rendering.ru.md) | **[done]** |
| Scripts | конфигурация сборки C++ (Debug, Release); набор инструментов зависит от машины и лежит в настройках редактора, см. [скрипты](scripting.ru.md); потом Luau | **[planned, step 3]** |
| Physics | гравитация, слои, матрица столкновений | **[planned, step 6]** |
| Audio | общая громкость, частота | **[planned, step 7]** |
| Display | разрешение, полноэкранный режим, можно ли менять размер окна | **[planned, step 9]** |
| Build | целевые платформы (Windows, Linux), сцены в игре, папка вывода, debug или release | **[planned, step 9]** |

Стартовая сцена живёт в General (`GeneralSettings::startupScene`); в
`project.yqlora` остались только имя проекта и версия движка **[done]**.

## Регистрация

```cpp
class PhysicsSettings final : public SettingsSection {
public:
    YQLORA_TYPE(PhysicsSettings, SettingsSection)   // имя типа, как у узлов

    Vec3 gravity{0.0f, -9.81f, 0.0f};
};

registry.registerSettings<PhysicsSettings>("physics")  // settings/physics.json
    .property("gravity", &PhysicsSettings::gravity);
```

`SettingsSection` - корень разделов, как `Node` и `Component`. Имя файла, имя
типа и поля записаны один раз **[done]**. В файле лежат версия формата и
значения в `values`, поэтому свойство с именем `version` не спорит с ключом
формата.

## Доступ

- Проект владеет одним экземпляром каждого зарегистрированного раздела
  (`ProjectSettings`), созданным со значениями по умолчанию и заполненным из
  его файла. Нет файла - значения по умолчанию; файл раздела, который больше
  никто не регистрирует, не трогается вовсе, чтобы модуль, который не
  загрузился, не потерял свои настройки **[done]**.
- Система читает свой раздел из проекта, с которым работает:
  `project.settings().get<PhysicsSettings>()` **[done]**. Запуск игры без
  редактора (шаг 9) читает те же файлы.
- Разделы модуля игры пересоздаются при перезагрузке модуля, чтобы в проекте
  не осталось объектов из выгруженной dll **[planned, step 3]**.
- Все настройки применяются сразу, в том числе во время Play. Перезапуска не
  просит ни одна: даже новый графический API пересоздаёт только рендер (см.
  [рендер](rendering.ru.md)) **[done]**.

## Окно

**Проект -> Настройки проекта**: слева разделы, справа свойства выбранного,
их рисует та же таблица свойств, что и в инспекторе. Папка настроек и файл
проекта скрыты в панели "Файлы", и менять их там нельзя. Над разделами окно
показывает версию проекта (формат файлов проекта) просто текстом: это не
настройка, она меняется только переводом проекта, а не руками. Версия самой
игры, для игроков, - это `gameVersion` в General, её можно править **[done]**.

## Слои

Как Tags and Layers в Unity:

- 32 слоя. Слой 0 - `Default`, есть всегда и не переименовывается; остальным
  имена даёт проект. Слой без имени не используется и в списках не
  показывается.
- Узел и маска камеры хранят номера слоёв, поэтому переименование слоя в
  сценах ничего не меняет. Если стереть имя слоя, на котором ещё есть узлы,
  редактор сначала спросит, а узлы останутся на нём. Узлы ищутся во всех
  сценах проекта (открытая - с несохранёнными правками, остальные - из
  файлов); маски камер не считаются, маска "Все" покрывает и слои без имени.
- Список слоёв в инспекторе и маска камеры показывают имена и кончаются
  пунктом "Изменить слои...", который открывает этот раздел. Слой без имени
  всё равно виден, пока он выбран, - номером.
- `LayerSettings` (scene/) хранит ровно 32 имени; редактор показывает их
  строками постоянного числа, строка `Default` выключена **[done]**.
- Физика (шаг 6) берёт те же слои для своей матрицы столкновений.

## Что нужно реестру

- Свойства-списки (действия, привязки, слои): `PropertyType::List` с типом
  элемента, любым типом свойства, кроме списка; поля `std::vector<T>`
  регистрируются как списки, JSON пишет их массивами, инспектор - строками с
  добавлением и удалением **[done]**.
- Записи: C++-структура, которая хранится целиком (`PropertyType::Record`,
  `RecordValue` со значениями полей по порядку). Поля описываются один раз
  рядом со структурой макросом `YQLORA_RECORD` (`reflection/Record.hpp`); из
  этого свойство получает описания полей (`Property::fields`), JSON пишет
  объект по именам полей (недостающее поле берёт значение из `T{}`),
  инспектор рисует поля маленькой таблицей. Поле записи само может быть
  списком или записью; списками записей хранятся Execution Order и действия
  ввода **[done]**.
- Свойство-привязка: строка с `PropertyHint::InputControl`, в редакторе
  задаётся нажатием **[done]**.
- Вид настроек (`TypeKind::Settings`) и его построитель **[done]**.
