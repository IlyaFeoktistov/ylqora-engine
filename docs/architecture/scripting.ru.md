# Скрипты

[English version](scripting.md)

Скрипт - это компонент (см. [сцену](scene.ru.md)): он живёт на узле и в
любом языке является своим типом компонента. Здесь языки и горячая
перезагрузка.

Пометки статуса: см. [README](README.ru.md).

## Языки

**Языки скриптов:** сначала C++ (MVP), после MVP - Luau, после 2D -
   визуальные скрипты.

## Границы: одна система поведения, несколько языков

Поведение пишется на C++ сейчас, на Luau и визуальными графами потом. Общее у
них всё, кроме того, как выполняется код:

```
Редактор, инспектор, сохранение, палитра графов, привязки Luau
        |   читают только реестр типов
Реестр типов: типы, свойства (с атрибутами), методы, фазы,
              модуль, "это скрипт"
        |   заполняют
C++-классы (ClassTypeBuilder)    скрипты Luau, визуальные графы (TypeBuilder)
        |   экземпляры - это
Component: контракт жизненного цикла (onEnable ... onStop), списки фаз,
           enabled, узел-владелец
        |   реализуют
класс игры на C++ : Script       LuauScript (VM)      VisualScript (граф)
```

- **Контракт - это `Component`.** Жизненный цикл, списки фаз, включение и
  перехват исключений есть у каждого компонента; языковой бэкенд решает
  только, что делает вызов.
- **Реестр типов - единственный источник метаданных.** Свойство описано
  значениями и функциями доступа, поэтому поле C++, переменная Luau и вход
  графа - одно и то же свойство. Инспектор, сохранение и меню свойства не
  знают, на каком языке поле.
- **Атрибуты поля живут в `Property`** (диапазон, отображаемое имя,
  подсказка, группа, не сохранять, не показывать), поэтому их сразу
  получают все языки.
- **"Это скрипт"** - пометка типа в реестре, её ставит каждый бэкенд;
  "Добавить компонент" собирает скрипты по ней. Это не базовый класс.
- **`Script` - база только для скриптов на C++**: удобство поверх контекста
  движка, который у компонента уже есть (`node()`, `transform()`,
  `input()`, `time()`, `scene()`). Скрипты Luau и визуальные не наследуют
  его; то же самое они дают через свои привязки, созданные по реестру.
- **Слоя `ScriptInstance` нет.** Luau и графы - по одному C++-классу
  компонента (`LuauScript`, `VisualScript`), привязанному к своему ресурсу,
  с типом, зарегистрированным во время выполнения; через C++-переходник
  ничего не идёт.
- **Модули владеют своими типами**: C++-библиотека игры, `luau`, `visual`.
  Имя типа, занятое другим модулем, отклоняется; выгрузка модуля сначала
  уничтожает его экземпляры.
- **Постоянные идентификаторы - имена, переименования явные.** В файлах -
  имя типа (`"Player"`) и имена свойств (`"speed"`), никогда не адреса и
  ничего из библиотеки; имена оставляют разницу читаемой, а у C++-класса нет
  своего файла, чтобы хранить GUID. Переименование объявляется там, где
  оно сделано: `field("speed", ...).formerly("moveSpeed")`,
  `registerScript<Player>().formerly("Hero")`: старое имя читается, новое
  пишется, значение не теряется. Скрипты Luau - файлы, поэтому их типы
  позже смогут идти за ID ресурса скрипта.
- **Без молчаливой потери данных.** Компонент, тип которого пропал, хранит
  свой объект JSON ровно таким, каким прочитан, и пишет его обратно без
  изменений. Свойства, которых у известного типа больше нет, тоже хранятся
  при объекте и пишутся обратно, поэтому убрать поле и вернуть его можно
  без потерь.

## Скрипты на C++ [done]

```cpp
class Player : public yqlora::Script {
public:
    YQLORA_SCRIPT(Player)

    float speed = 5.0f;

    // Внутри класса, поэтому можно перечислить и закрытые поля.
    YQLORA_FIELDS(
        field("speed", &Player::speed).range(0.0f, 100.0f).tooltip("player.speed.tooltip"),
        field("jumpHeight", &Player::m_jumpHeight)
    )

protected:
    void onUpdate(float deltaSeconds) override
    {
        const Vec3 move(input().actionValue("MoveX"), 0.0f, -input().actionValue("MoveY"));
        transform().translate(move * speed * deltaSeconds);
    }

private:
    float m_jumpHeight = 1.5f;
};

// Единственная точка входа модуля игры; в шаге 2 пишется руками, в шаге 3 -
// генератором.
YQLORA_MODULE_ENTRY(registrar)
{
    registrar.registerScript<Player>();
}
```

### Решения

- **Скрипт - это компонент**, а не параллельная система объектов: тот же
  узел, жизненный цикл, списки фаз, сохранение и инспектор, что у любого
  компонента.
- **Поля перечисляются явно**, а не берутся по модификатору доступа: поле
  сохраняется и показывается, потому что оно перечислено, открытое или
  закрытое. Имя в `field("speed", ...)` - постоянный идентификатор в файлах;
  подпись в инспекторе отдельно (`property.<name>` или `displayName`).
  Описание поля может расти, не ломая скрипты: диапазон, отображаемое имя,
  подсказка, группа, флаги "не сохранять" и "не показывать" (список полей -
  это метаданные; сохранение и инспектор - два их пользователя).
- **Типы полей** - типы свойств реестра: bool, int, float, строка, векторы,
  цвет, перечисления, `NodeRef`, `ResourceRef`, списки и записи. Ссылки на
  узлы и ресурсы - постоянные ID, никогда не указатели.
- **Явная регистрация на модуль**: одна входная функция библиотеки
  (`YQLORA_MODULE_ENTRY`) регистрирует свои скрипты через полученный
  `ModuleRegistrar`, который записывает их на модуль; никаких глобальных
  статических регистраторов и зависимости от порядка статической
  инициализации. Занятое имя типа (другим модулем, тем же модулем второй
  раз или как прежнее имя) не регистрируется: оно попадает в `rejected()`
  вместе с модулем, которому принадлежит, и загрузчик сообщает об этом, не
  роняя редактор. После `registerScript<T>()` в цепочке только правила типа:
  `formerly`, `requiresNode`, `requiresComponent`, `executionOrder`; поля -
  из `YQLORA_FIELDS`.
- **API скрипта** (`node()`, `transform()`, `input()`, `time()`,
  `scene()`, поиск узлов, лог) - удобство поверх контекста движка, который у
  компонента уже есть через его сцену; `Script` не владеет ни одной
  подсистемой.

### Контракт жизненного цикла

Жизненный цикл компонента из [сцены](scene.ru.md), как его видят скрипты:

| Вызов | Когда |
|---|---|
| `onEnable` | скрипт начинает участвовать: включён и его узел активен в иерархии; до `onStart` |
| `onStart` | один раз за запуск, до первого вызова фазы; повторное включение его не повторяет |
| `onFixedUpdate(step)` | каждый фиксированный шаг игрового времени (физика) |
| `onUpdate(delta)` | каждый кадр |
| `onLateUpdate(delta)` | после всех `onUpdate` кадра |
| `onDisable` | сразу, когда выключают скрипт или его узел, до `onStop`; никогда дважды: снятие уже выключенного скрипта его не повторяет |
| `onStop` | игра остановлена или скрипт сняли или уничтожили; только после `onStart` |

- Скрипт, выключенный до первого запуска, не получает `onStart`, пока его
  не включат.
- Скрипт, выключивший себя в `onUpdate`, сразу получает `onDisable` и до
  конца фазы пропускается; из списка он уходит после фазы.
- Порядок внутри фазы: порядок выполнения типа, затем порядок входа (см.
  [сцену](scene.ru.md) и Execution Order в настройках проекта).
- Исключение из вызова выключает скрипт и уходит в лог.

### Модуль игры

- Скрипты игры - одна разделяемая библиотека, модуль игры: один на проект,
  регистрируется на модуль типов `game` (`GameModule::moduleName`). Лежит в
  `<проект>/.build/game.dll` (`libgame.so`, см. `gameLibraryPath`); до шага 3
  собирается руками (см. [руководство "Первый скрипт"](../guide/first-script.ru.md)).
- `GameModule::load` открывает библиотеку, находит `YQLORA_MODULE_ENTRY` по
  `kModuleEntrySymbol` и вызывает её с `ModuleRegistrar`. Нет библиотеки или
  входной функции - ошибка в логе, а не падение; отклонённое имя типа
  пишется в лог, остальной модуль работает.
- `GameModule::unload` уничтожает все компоненты модуля в переданных сценах,
  потом убирает его типы, потом выгружает библиотеку. В редакторе порядок
  держит `EditorSession`: модуль загружается до стартовой сцены и
  выгружается после сцены и истории правок.
- Без библиотеки проект всё равно открывается: его скрипты ждут заглушками
  (`MissingComponent`) и возвращаются вместе с библиотекой.

### Ограничения

- **Нативному коду доверяют.** Скрипты выполняются в процессе редактора.
  Исключение из вызова жизненного цикла выключает компонент и идёт в лог;
  падение или бесконечный цикл роняет редактор. Язык с песочницей - Luau
  (после MVP).
- **Один модуль игры на проект**, собранный тем же компилятором и для той же
  версии движка, что и редактор.
- **Luau и графы ложатся в те же границы**: их типы попадают в тот же
  реестр на свои модули (`luau`, `visual`), помечены как скрипты, а их
  экземпляры - компоненты одного C++-класса на язык (`LuauScript`,
  `VisualScript`). Выше реестра ничего не меняется; от `Script` они не
  наследуются.

## Скрипты на Luau [planned, after MVP]

[Luau](https://luau.org) (MIT): Lua 5.1 с постепенной типизацией, встроенной
песочницей и языковым сервером.

- Каждый скрипт `.luau` регистрирует **свой тип компонента** с именем
  скрипта и свойствами, объявленными в скрипте. Все они создают экземпляры
  одного C++-класса, `LuauScript`, привязанного к ресурсу скрипта. Реестр
  принимает такие типы без своего C++-класса, см.
  [типы и рефлексию](reflection.ru.md).
- Привязки генерируются из реестра: свойства и методы типов. Один список
  служит Luau, инспектору и документации API. Из того же списка получаются
  файлы определений типов для luau-lsp, которые дают автодополнение и
  проверку типов в редакторе кода.
- Песочница: собственная у Luau (`luaL_sandbox`: глобальные только для
  чтения, нет доступа к `io` / `os`), обработчик прерываний против
  бесконечных циклов, распределитель памяти с ограничением.
- Ошибка Luau выключает компонент и идёт в лог, как исключение C++.
- Скрипты Luau - свой модуль типов (`luau`), перезагружаются как `game.dll`.

## Визуальные скрипты [planned, after 2D]

Для тех, кто не пишет код: скрипт собирается из блоков, соединённых связями,
потом вешается на узел и работает как скрипт на C++ или Luau.

- Граф - ресурс (файл проекта): блоки, их выводы и связи между ними. Связи
  выполнения задают порядок действий, связи данных передают значения.
- Каждый граф регистрирует **свой тип компонента**, как скрипт Luau, со
  свойствами, объявленными в графе. Все они создают экземпляры одного
  C++-класса, `VisualScript`, привязанного к ресурсу графа.
- Входные блоки - вызовы жизненного цикла (`onStart`, `onUpdate`, `onStop`),
  позже события (ввод, столкновения).
- Палитра блоков генерируется из того же списка реестра, что и привязки Luau:
  свойства и зарегистрированные методы типов движка и игры. Новый метод типа
  становится блоком без дополнительной работы.
- Движок интерпретирует граф. Ограничение числа шагов на вызов защищает от
  бесконечных циклов; ошибка выключает компонент и идёт в лог, как исключение
  C++.
- Визуальные скрипты - свой модуль типов (`visual`), перезагружаются при
  сохранении графа.
- Редактор графов - панель редактора; логика правки отделена от ImGui, как и
  весь редактор.

## Сборка и горячая перезагрузка [planned, step 3]

Цикл: правишь скрипт в IDE, переключаешься в редактор, и редактор собирает
модуль игры, перезагружает его и возвращает сцену с теми же значениями
полей; ошибки компилятора видны в логе редактора.

### Решения

- **Что пересобирать, решает Ninja.** Редактор запускает `cmake --build`,
  когда его просят, и сам за файлами не следит: Ninja знает настоящие
  зависимости (заголовки, найденные компилятором, флаги, конфигурацию).
  Когда делать нечего, сборка - почти пустая проверка, а модуль
  перезагружается, только если собранная библиотека изменилась.
- **Движок - переносимый CMake-пакет.** Сборка движка кладёт рядом с
  программой SDK (`sdk/`: публичные заголовки, библиотека импорта,
  `yqloraConfig.cmake`); каждый путь в нём вычисляется от места самого
  пакета, никогда не записывается абсолютным, поэтому перенесённый редактор
  по-прежнему собирает проекты. `find_package(yqlora)` даёт
  `yqlora::yqlora`, а `yqlora_add_game_module(<цель> <исходники>)` держит все
  правила библиотеки игры. В SDK есть glm, но нет ImGui: код игры рисует
  через движок, а не через набор виджетов редактора.
- **Результат называет CMake.** Пакет записывает `$<TARGET_FILE>` модуля
  игры в папку сборки; редактор берёт путь оттуда и сам имя библиотеки не
  составляет.
- **Набор инструментов воспроизводит ABI редактора.** Сборка движка
  записывает свой набор: компиляторы C и C++ с типом и версией, Ninja,
  архитектуру, библиотеку времени выполнения MSVC и как поднять окружение
  Visual Studio (`vcvarsall`) для MSVC. Сборка проекта идёт по этой записи,
  поэтому скрипт собран так же, как движок, в который он загружается.
  Конфигурация (Debug, Release; настройки проекта, раздел Scripts) меняет
  только оптимизацию, никогда библиотеку времени выполнения.
  Переопределения - в настройках редактора (`editor.json`): пути зависят от
  машины и в git не идут. Сменившийся набор инструментов даёт новую папку
  сборки, а не старый `CMakeCache.txt`.
- **Каждая загрузка - новая копия.** Собранная библиотека перед загрузкой
  копируется в `.build/reload/game_<n>`, поэтому загруженный файл никогда не
  перезаписывается (Windows его блокирует), а каждая перезагрузка видна на
  диске. Незагруженные копии удаляются при открытии и закрытии проекта.
- **Лог - буфер, а не вызовы в интерфейс.** Подписчики лога вызываются вне
  его блокировки и отписываются через владеющий объект; сборка пишет в
  потокобезопасный `LogBuffer` из своего потока, а редактор забирает новые
  записи в главном потоке.
- **Процесс, диагностика и лог - три части.** `platform::Process` запускает
  программу и читает stdout и stderr по мере поступления (UTF-8, код
  завершения, аварийное завершение, остановка, без блокировки главного
  потока); `CompilerDiagnostics` превращает строку GCC, Clang или MSVC в
  структурную запись (файл, строка, столбец, уровень); лог только хранит
  записи.
- **Одна сборка за раз.** Запрос во время сборки ставит один флаг; сколько
  бы запросов ни пришло, после текущей сборки запускается ещё одна.

### Перезагрузка

После успешной сборки, если библиотека изменилась (порядок держит
`EditorSession`):

1. Остановить Play; закончить текущую правку.
2. Сериализовать редактируемую сцену в память, пока старый модуль ещё
   загружен, чтобы каждое поле скрипта прочитал его собственный код. Файл на
   диске не трогается, поэтому пометка "не сохранено" остаётся какой была.
3. Очистить историю правок: команды держат живые объекты (снятые
   компоненты, удалённые ветки), чей код уходит вместе с модулем. Лог
   сообщает об этом.
4. Уничтожить все компоненты модуля (`GameModule::unload` проверяет, что в
   сценах их не осталось), убрать его типы, выгрузить библиотеку.
5. Скопировать новую библиотеку в `.build/reload/game_<n>`, загрузить,
   зарегистрировать её типы.
6. Прочитать сцену обратно из памяти, восстановить выделение.

Неудачи:

- **Сборка не прошла**: старый модуль и сцена не трогаются; ошибки в логе.
- **Новая библиотека не загрузилась или её входная функция не прошла**
  (бросила исключение): регистрация откатывается (`removeModule`,
  библиотека выгружается), полузарегистрированных типов не остаётся; сцена
  возвращается с заглушками (`MissingComponent`), в которых все данные, и
  оживает со следующей удачной сборкой. Чтение сцены - всё или ничего
  (дерево собирается отдельно и ставится, только когда готово целиком).

Тесты, кроме модульных тестов каждой части: изменение только заголовка
пересобирает модуль (настоящая сборка CMake временного проекта); исходник,
изменённый во время сборки, запускает ещё одну сборку; библиотека, чья
входная функция бросает исключение, не оставляет ни типов, ни компонентов;
значения полей скриптов те же после нескольких перезагрузок и сохранения;
после выгрузки в сценах нет ни одного компонента модуля, а в реестре - ни
одного его типа.

До генератора (после MVP) новый скрипт регистрируется строкой в
`Module.cpp`: найти скрипты в исходниках можно только разбором C++, а
регулярные выражения исключены.

Компонент, тип которого пропал (игра не собралась, скрипт удалили),
сохраняется как заглушка с его сырыми данными, показывается в инспекторе как
не найденный и записывается обратно без изменений при сохранении; после
перезагрузки `reviveMissing` возвращает его. Иначе сохранение сцены молча
потеряло бы данные **[done]**.
